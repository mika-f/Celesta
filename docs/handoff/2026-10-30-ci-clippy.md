# Clippy in CI (2026-10-30)

Issue #601. `HANDOFF.md` lists two clippy commands, but CI never ran either,
and the workspace one failed on `main`. Pull requests #583, #587, #590, #593,
and #594 each worked around it with `-A clippy::large_enum_variant`.

## Findings on `main`

With clippy 0.1.99 (rustc 1.99.1, the toolchain CI pins):

- `cargo clippy --workspace --all-targets --locked --keep-going -- -D warnings`
  reported one lint, `clippy::large_enum_variant` on `SourceLookup` in
  `crates/editor/src/layer_select.rs`, for both the `celesta-editor` binary and
  its test target. `Found(LayerSourceReport)` was 232 bytes and the next
  largest variant, `Failed(String)`, 24. Every other crate was clean.
- `cargo clippy -p celesta-composition -p celesta-project --all-targets
  --features codegen --locked -- -D warnings` passed. ts-rs prints "failed to
  parse serde attribute" for `transparent` and `deserialize_with`; the ts-rs
  derive prints these itself, they are not rustc lints, and `-D warnings` does
  not turn them into errors.

## Specification and implementation

- **CI.** The `test` job in `.github/workflows/ci.yml` installs the `clippy`
  component with the pinned toolchain and, on Linux only, runs both
  `HANDOFF.md` commands with `--locked` and `-D warnings` after the tests.
  Linux finishes minutes before Windows, so the step adds no time to the
  workflow; only a few files hold code behind a `cfg` for one OS. The step
  reuses the job's FFmpeg, apt packages, and rust-cache, but not the Build
  step's artifacts: clippy compiled the proc macros and build scripts again
  and checked every dependency. main's cache had no clippy output yet: on the
  passing run both commands took 2 min 6 s, the Linux job 7 min 58 s, and the
  Windows job 12 min 8 s. Once main saves a cache with the check output, pull
  requests should spend less. rust-cache keys on
  `rustc -vV` and the listed environment variables, not on the installed
  components, so adding `clippy` keeps main's cache key. No action was added,
  so `.github/workflows/actions.lock` is unchanged.
- **`SourceLookup`.** `Found` now holds `Box<LayerSourceReport>`, so the enum
  no longer takes the report's 232 bytes. The report moves to the heap
  rather than going away: each `Found` costs one allocation, and reading the
  report follows a pointer. The editor stores one `Option<SourceLookup>`
  (`EditorView::source_lookup`), never clones or collects it, and replaces it
  once per lookup answer (a selection or a paused frame), so neither the
  enum's size nor the allocation is expected to matter. Neither was measured.
  Keeping the report inline with
  `#[expect(clippy::large_enum_variant, reason = "…")]` would be as
  reasonable; the box follows the lint's suggested fix and passes CI as is.
  Sites that hand the report on as `&LayerSourceReport` inside a tuple or an
  `Option` dereference the box (`&**report`).
- **Convention.** `HANDOFF.md`'s working conventions now say how to resolve
  clippy findings: check the cause and the usage, weigh the suggested change
  against keeping the code, and keep it with a reasoned `#[expect]` on the
  item; never `-A` or a `clippy.toml` threshold.

## Checks

On macOS (Apple M5) with Rust 1.99.1:

- Both `HANDOFF.md` clippy commands, with `--locked`, passed after the fix.
- `cargo test -p celesta-editor --locked`: 651 passed.
- `cargo fmt --all -- --check` and `git diff --check` passed.
