# BT.709 export color and nv12/p010 readbacks, P2c (2026-11-08)

Phase P2c of the media components design
(`docs/superpowers/specs/2026-11-08-media-components-design.md`; plan
`docs/superpowers/plans/2026-11-08-media-components-p2c.md`), on top of
P2b (`docs/handoff/2026-11-08-media-pipelining.md`). Every video export is
BT.709 with limited range: the GPU converts with that matrix, every FFmpeg
encoder is given the `Color` and applies it, and every container is tagged
from it. MP4 output changes from untagged BT.601 to tagged BT.709; MOV and
WebM decode identically to P2b's.

## Specification

- **The matrix** (`crates/gpu-renderer/src/yuv420p.wgsl`). In 8-bit codes,
  `Y' = 16 + 219·(0.2126 R + 0.7152 G + 0.0722 B)`,
  `Cb = 128 + 224·(B − Y)/1.8556`, `Cr = 128 + 224·(R − Y)/1.5748`, as the
  coefficients `Y' = 16 + (46.559, 156.629, 15.812)·RGB`,
  `Cb = 128 + (−25.664, −86.336, 112.0)·RGB`,
  `Cr = 128 + (112.0, −101.730, −10.270)·RGB`. Chroma is the mean of each
  2x2 block; 10-bit codes are the 8-bit value times four; each plane is
  rounded with `dither.wgsl` as before. The input is full-range
  sRGB-encoded RGB.
- **Four YUV readbacks** (`ReadbackFormat`): `Yuv420p` (Y, U, V planes, one
  byte a sample), `Yuv420p10` (the same in 16-bit little-endian words),
  `Nv12` (Y plane, then interleaved UV written to one `Rg8Unorm` target),
  and `P010` (16-bit little-endian Y, then interleaved UV in one `Rg16Uint`
  target, the 10-bit code shifted left by 6). Sizes: `yuv420p` and `nv12`
  are `width × height × 3 / 2` bytes, `yuv420p10` and `p010` `width ×
  height × 3`, so P2b's ring slots need no new size. All four need even
  dimensions (`GpuRenderError::OddYuv420pSize`).
- **Offered formats** (`crates/exporter/src/encode.rs`), best first:
  `yuv420p`, `yuv420p10`, `nv12`, `p010` when the renderer
  `supports_yuv420p_readback()` and is not `is_software()` (deviation 18,
  kept), then `rgba16`, then `rgba8`. `readback_of` maps the six.
  `PixelFormat::OFFERABLE` (`crates/media/src/provider.rs`) lists the same
  six, which sizes the ring: `ring_layout(&[Nv12, P010], 1920, 1080)` is
  three slots of 6,220,800 bytes (ruling R1; P2b's ring test changed).
- **Applying `Color`** (`plugins/ffmpeg/src/tags.rs`, `AvColor`). Names are
  libavutil's (`av_color_primaries_from_name`, `av_color_transfer_from_name`,
  `av_color_space_from_name`; `range` maps `limited`, `tv`, `mpeg` to
  `AVCOL_RANGE_MPEG` and `full`, `pc`, `jpeg` to `AVCOL_RANGE_JPEG`) and
  round-trip exactly. A name libavutil does not know is
  `MediaError::Codec("unknown color {field} `{name}`")` at `open`, never a
  silent default. Every video encoder (libx264, ProRes, VP9) tags its codec
  context and each frame. An encoder given RGB converts with libswscale's
  table for the matrix (`SWS_CS_ITU709` for `bt709`, `SWS_CS_ITU601` for
  `bt470bg` and `smpte170m`, `SWS_CS_BT2020` for `bt2020nc`; another matrix
  is an error), passing the table as both source and destination table of
  `sws_setColorspaceDetails` (ruling R4), so MOV and WebM output is
  byte-identical in its decoded video to P2b's.
- **libx264** takes `nv12` directly, as libavcodec's `libx264` lists it. It
  lists no 10-bit semi-planar 4:2:0 format, so `p010` is repacked to
  `yuv420p10le` with libswscale (`SWS_POINT`, no color change). It prefers
  `yuv420p` and `yuv420p10` when offered, so from Celesta it never needs
  either repack. Its `inputFormats` are
  `yuv420p`, `yuv420p10`, `nv12`, `p010`, `rgba8`, `rgba16`.
- **Muxers** tag every video track from `Track.color` with
  `AvColor::apply_to_codecpar`, with no family filter (the ap4h/apch/vp09
  filter and `tag_color` are gone, ruling R5): MP4 gets `colr` `nclx`, MOV
  `colr` `nclc`, WebM `Colour` (MatrixCoefficients, Range,
  TransferCharacteristics, Primaries). libavformat (FFmpeg 8.1) writes
  `colr` whenever primaries, transfer, and matrix are all set on `codecpar`,
  with no muxer flag. H.264's VUI is written by x264 from the context.
- **Unchanged.** `celesta_media::Color` on the wire (P2a); stills
  (`--frame`, contact sheets), which are RGBA; input decoding
  (`plugins/ffmpeg/src/color.rs`, `celesta_media::VideoColor`); the macOS
  native preview's NV12 (`native_preview.wgsl`), which tells CoreVideo its
  own matrix.

## Known colors

8-bit codes (Y, Cb, Cr) of full-range sRGB primaries, BT.709 limited; the
GPU readbacks and libswscale's 8-bit path agree on them:

| Color | Y | Cb | Cr |
| --- | --- | --- | --- |
| red | 63 | 102 | 240 |
| green | 173 | 42 | 26 |
| blue | 32 | 240 | 118 |

At 10 bits the formula's codes are red (250, 409, 960), green (691, 167,
105), blue (127, 960, 471). libswscale's 16-bit-RGB to 10-bit path, which an
encoder converting `rgba16` itself takes, gives red (251, 409, 962), green
(693, 165, 103), blue (128, 962, 471), up to 2 codes off (ruling R10); the
encoder test `rgba_input_is_converted_with_bt709` pins libswscale's codes
(BT.601's red Y would be about 326).

## Deviations from the spec

Numbered after P2a's 8–18 and P2b's 19–28; recorded in the spec's Pixel
formats and color and Phases sections.

8. (P2a's) ends: `Color` is applied everywhere.
18. (P2a's) is kept: a software renderer is offered no YUV format, so
    CI's software renderers keep their encoder-side conversion. Now with
    four YUV formats left out rather than two.
30. **The test codec stores no color.** `celesta-codec-test`'s file has no
    reader but Celesta's tests, so its components accept `Color` and
    `Track.color` and store nothing. The exporter's `encode.rs` tests pin
    the `Color` the muxer receives.
31. **The GPU reference is Celesta's formula.** The GPU tests compare with a
    CPU function of the formula, within the dither's one code (exact on
    whole codes). Its 8-bit codes equal libswscale's for every color
    checked; libswscale's own 16-bit-RGB to 10-bit path differs from the
    formula by up to 2 codes (blue's Cb 962 against 960, red's Y 251
    against 250), so the encoder tests pin libswscale's codes (ruling R10).

Rulings that changed behavior or tests:

- R1: `PixelFormat::OFFERABLE` gained `nv12` and `p010`; P2b's ring test and
  the `PixelFormat` docs changed with it, and the spec's Transport deviation
  20 now lists six formats.
- R4: the RGB scaler's source table is the color's table, as ProRes and VP9
  passed before, rather than `SWS_CS_DEFAULT`.
- R9: the `p010` GPU test's "equal where the reference is within 0.125 of a
  whole code" is within 1/128 at 10 bits (the 8-bit path snaps to whole
  codes; the 10-bit one does not); the within-one-code bound still holds
  everywhere.
- R10: see Known colors.
- R11: `mov_and_webm_stay_tagged_bt709_and_mp4_untagged` became
  `mp4_mov_and_webm_are_tagged_bt709`, which Task 5 extended to range,
  `colr`, and `Colour`.

### Against P2b (`0942fedb`)

`film.tsx` (1920x1080, 60 fps) from 1.5 s to 2.0 s (30 frames, film frame 90
is IGNITION's gradient lights and title), exported as MP4, MOV, and WebM
with P2b's exporter and plugin and with this branch's, the same React
runtime for both. Tools: Homebrew's `ffmpeg@8` `ffmpeg` and `ffprobe`.

Tags (`ffprobe` `color_space`, `color_primaries`, `color_transfer`,
`color_range`):

| File | Tags |
| --- | --- |
| P2b MP4 | unknown, unknown, unknown, unknown |
| P2c MP4 | bt709, bt709, bt709, tv |
| P2b and P2c MOV (ProRes 4444) | bt709, bt709, bt709, tv |
| P2b and P2c WebM (VP9) | bt709, bt709, bt709, tv |

Decoded colors, as a BT.709 player decodes (`scale=in_color_matrix=bt709:in_range=tv`),
PSNR against the RGBA still of the same frame (`--frame 90`):

| File | Decoded as | PSNR average (dB) |
| --- | --- | --- |
| P2b MP4 | BT.709 | 37.72 |
| P2c MP4 | BT.709 | 39.92 |
| P2b MP4 | BT.601 | 40.14 |
| P2c MP4 | BT.601 | 36.86 |
| MOV, P2b and P2c | BT.709 | 53.13 |
| WebM, P2b and P2c | BT.709 | 41.18 |

The MP4's gain is 2.2 dB on this scene, not several: it is dark and
low-saturation, so the matrix shift moves few codes (green gains 6.8 dB, red
1.4, blue 0.6). P2b's MP4 decoded as BT.601 is within 0.23 dB of P2c's
decoded as BT.709, so the two differ by the matrix and nothing else.

`cmp`:

- Decoded video (`-pix_fmt rgba64le`, 30 frames, 497,664,000 bytes): MOV and
  WebM identical between P2b and P2c; MP4 differs from byte 1, as expected.
- `--frame 90` PNGs from P2b's exporter, P2c's, and the reference are
  byte-identical (sha256 `959a0f86…42b04`).
- Audio (the scene has none, so a 640x360, 90-frame scratch entry with one
  `<Audio>` of `examples/assets/voices/001.wav`): MP4 (AAC), MOV (PCM), and
  WebM (Opus) decode to identical samples between P2b and P2c.

Timing (release build, 30-frame MP4, six runs interleaved, wall time): P2b's
median 0.751 s (0.696 to 0.818), P2c's 0.756 s (0.722 to 0.785). The machine
was not quiet: load averages ran 8 to 22 throughout, so these are not
quiet-machine numbers; P2c's median is inside P2b's spread, and the matrix
change costs nothing by construction (the shader's arithmetic is the same
size). A 30-frame export is also short and noisy.

The before and after images for the PR (the RGBA reference, P2b's MP4, and
P2c's MP4 at film frame 90, decoded as BT.709) are attached to the pull
request, as AGENTS.md asks of a rendering change.

## Not done

- **Presets and the export dialog** (P3): there is no way to choose a color
  yet; every export is BT.709 limited.
- **Stills through components** (P4): stills stay RGBA, unchanged.
- **OS-native plugins** (P5, P6): VideoToolbox is expected to take `nv12`
  by itself whatever the offered order; Media Foundation is not started.
- **HDR and other matrices**: `Color` is sent as BT.709 only; an encoder
  that gets another name converts RGB with a libswscale table for it where
  one exists (`bt470bg`, `smpte170m`, `bt2020nc`) and refuses the rest.
- **Deferred minors from review**: the 10-bit `tests.rs` comment's red U
  "409.4" is 409.34; the GPU readback labels still say "yuv420p" for `nv12`
  and `p010`; the integration `nv12`/`p010` test skips silently without YUV
  and ignores `CELESTA_REQUIRE_GPU`; tags.rs comments claim libavutil's
  `from_name` prefix-matches where FFmpeg 8's is exact; an RGB-input matrix
  with no libswscale table is refused after `avcodec_open2` rather than
  right after `from_color`; `stream_color` is duplicated in
  `plugins/ffmpeg/tests/process.rs` and `export.rs`.
