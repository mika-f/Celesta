# Exporter and MCP cleanup (#704)

- Project audio mixing signals failure to the frame loop before it starts another frame or drains the renderer. The original mix error is kept, and the session aborts before its staged file drops. This complements the frame-by-frame polling introduced by the media-component rewrite. React still collects its audio graph during rendering.
- CLI and MCP use the same loudness and range parsers and the stills library's option checks. Subtitles-only MCP calls reject `truePeak` and `peakHandling` even without a loudness target.
- React video, stills and quality checks share companion-project frame and font construction. The obsolete file, non-cancellable React video, and exact-frame stills wrappers are gone; their test callers use the cancellable APIs.
- `{lang}` output groups by trimmed lowercase tag, treating missing, blank and explicit `und` as one group. All subtitle destinations are planned, checked and staged before any final output is published. The final renames are individually atomic, not a group transaction.
- MCP waits for the rendering lock after stdio service shutdown, bounded to ten seconds. The blocking export owns the lock, so cancellation of its request cannot release it before staged files are cleaned up. Runtime tests cover stdin EOF and Unix SIGTERM with a staged video and an in-flight frame. A React frame blocked beyond the shutdown deadline can still leave a staged file.
- Bench workloads declare whether they need the generated image, stored in a `TempDir`. The script uses the source-kind column of each revision's benchmark list; old benchmark binaries fall back to their descriptions and the legacy names.

The `.pcm` sidecar was removed by the media-component rewrite. Tests cover the replacement packet-spill file dropping before finalization and no staged files left on project mix failure. A separate render test signals failure just after the per-frame poll and verifies that the next frame is not started and the renderer is not drained. Disabling the two render guards makes it fail: a two-frame window starts and encodes both frames, and a one-frame window encodes its pending frame during drain. The runtime PNG encoder now lives in `celesta-media-image`, not the exporter, and has an explicit default-byte-parity test plus named compression modes. Neither that encoder nor the exporter's test-only PNG dependency was changed here; replacing the production encoder needs a separate compatibility decision.

Checks: `cargo fmt --all -- --check`; `cargo test --locked -p celesta-exporter -p celesta-mcp -p celesta-media -p celesta-bench -p celesta-cli --features runtime-tests` with the built React runtime and Lavapipe; `cargo clippy --locked -p celesta-exporter -p celesta-mcp -p celesta-media -p celesta-bench -p celesta-cli --all-targets --features runtime-tests -- -D warnings -A unfulfilled-lint-expectations`. Strict Clippy also fails on the base revision's existing MCP `inspect.rs` lint expectation.
